> 2. 新增第 10 章「硬规则」——把散落的硬规则**内联**进协议，并同步回 3 份项目规则模板。

## 0. 总则
- 全程中文对话；用户本人不输入任何命令，所有终端/脚本操作由 AI 在需要时自行完成。
- 不使用任何后台常驻进程、定时任务、开机自启、文件监听；所有脚本**按需运行**，收尾时必须关闭 AI 本次开启的所有进程。
- 所有路径使用**相对路径**（本工作区可整体复制到任何电脑任何目录），不要写死绝对路径。
- 方向性决策由用户决定；AI 只提建议、做执行。
- 工作区结构：
  - `AI-Dev-Harness\自定义\`：用户可改（对话协议、流程、skills、templates、项目规则模板、scripts）。
  - `AI-Dev-Harness\内置\`：内置适配与脚本，**默认不要改动**（确有必要时见第 8 章）。
  - `AI-Dev-Harness\state\`：各项目归档（自动维护，不进项目）。
  - `.claude\`（工作区根）：机制层——hooks 与状态文件，**AI 不需要改它，但必须知道它存在**（见第 14 章）。
  - `.harness\`（项目内）：开发期工作文件（JOURNAL / HANDOFF / logs / bypass）。
  - `我的项目\`：项目文件夹（阶段 3 会被改名为项目名）。

## 1. 阶段 0 · 开工
1. **先体检**：跑 `node AI-Dev-Harness\自定义\scripts\env-doctor.mjs`（在项目目录内则用 `..\AI-Dev-Harness\...`）。
   - 它会报出模型窗口陷阱（模型名带 `[1M]` 时压缩阈值会被抬到 96.7 万）、hooks 是否注册、规则模板是否已升级、有无上次的 HANDOFF。
   - 它的输出末尾就是一份**可直接使用的启动词**；把它当作本会话的开工说明。
   - `--fix` **不要自动加**：修复必须由用户显式要求（决策 5）。
2. 用中文问候，询问用户「你想做什么项目？」（用户说一句话即可）。
3. **先问清「从零设计」还是「已有方案」**：用户手上已经有一份方案 / 计划文档时，请他放进项目文件夹
   （`我的项目\`，或改名后的项目目录）里的任意位置并说明路径 —— 铁律规定 AI 只能动项目文件夹与 `state\`，
   放在项目里才能既读又整理。**已有方案时走第 2 章的「已有方案」分支，不要重复从零讨论方案。**
4. 收到需求后，**先复述确认**，指出不清楚或可能冲突的地方，不急着动手。
5. 若 `env-doctor` 报出上次的 `HANDOFF.md`：先确认「下一步」，再动手，不要凭记忆重建上下文。

## 2. 阶段 1 · 方案沟通与确认

**已有方案文档时（走这条，别重复造方案）**：
1. 用 `plan-and-requirements` 技能**只读**核对：文档是否齐全、彼此是否冲突、有无缺失 / 模糊 / 不可行，列成清单给用户；
2. 逐条问用户确认（方向性决策由用户定，AI 不擅自替他改方向）；
3. 以已有文档为基准，**只补缺口**，不推翻重来；缺什么再问什么。

**从零设计时**（下面 1–3 步）：

1. 通过一步步中文对话，把项目聊清楚：做什么、主要功能、技术偏好（网页/桌面/脚本/语言框架）、是否发布等。用户说「你定」的项，AI 可给建议，但需用户认可。
2. AI 整理出「方案清单草稿」展示给用户，至少包含：需求清单、设计理念、功能模块、目录结构、验收标准。
3. 询问用户是否满意、是否要改；反复修改直到用户说「确认 / 可以生成方案」。

## 3. 阶段 2 · 文档生成与归档
用户确认后，在项目文件夹（此时还叫 `我的项目`）内生成两份文档：
- `方案.md`：整个项目的方案文档（目标、功能、技术方案、目录结构、实施步骤、验收标准）。
- `需求与理念.md`：整个项目的需求与理念文档（需求清单、设计理念、约束、交互原则）。
两份文档属于项目本身，永久保留，指导后续开发；模板见 `AI-Dev-Harness\自定义\templates\方案模板.md` 与 `需求与理念模板.md`。

> **用户已有方案文档时**：把它的内容**归并**成这两份（原文档按用户意愿保留或删除），以已有文档为基准补全体例，
> 不要另起一份与它矛盾的方案；归并后向用户展示「哪些是原文、哪些是补的」。

## 4. 阶段 3 · 项目命名与脚手架扩展
1. 询问用户是否给项目命名；
2. AI 根据方案推荐 3–5 个名字供用户选，或由用户自己起；
3. 用户确定名字后，AI：
   - 把 `我的项目` 文件夹改名为 `<项目名>`；
   - 在 `方案.md`、`需求与理念.md` 中写入项目名称；
   - 在 `AI-Dev-Harness\state\<项目名>\` 建立归档目录。
4. **跑脚手架扩展**（衔接点 E1）：
   - 复制项目规则模板到项目内：`CLAUDE.md` / `AGENTS.md`（Trae 用 `.trae\rules\project_rules.md`）。
   - 执行：`node AI-Dev-Harness\自定义\scripts\scaffold-ext.mjs --project "<项目目录>"`（第 5 批 · A13）。
     它补齐项目内 `.claude\`（hooks + `settings.json`）与 `.harness\`，让**从项目目录内启动的会话**
     也能拿到机制层保护 —— 终端模式下 cwd 就是项目目录，而 Claude Code **不向上继承**工作区根的 `.claude\`。
     它幂等、可重复跑；**不预生成 `HANDOFF.md`**（那是 `on-stop.mjs` 的产物，预先放一个空文件等于对模型撒谎）。
   - 核对：`node AI-Dev-Harness\自定义\scripts\scaffold-ext.mjs --check --project "<项目目录>"`，
     应报「项目内 hooks 与主副本逐字节一致」。
   - 若脚本确实不存在，**如实向用户说明「项目内机制层尚未生成」，不要假装做了**。
5. 项目内 `.gitignore` 补上运行时产物：`.harness\logs\`、`.claude\state\`（`scaffold-ext.mjs` 已自动补齐，核对一下即可）。

## 5. 阶段 4 · 项目执行与交付
命名后询问「现在开始执行吗？」，用户确认后才开始。

### 5.1 开发循环
1. 按 `方案.md` 搭建骨架、逐个功能开发；
2. 每完成一个小功能做**最小验证 = L1 定向验证**（见第 12 章），验证通过再进入下一步；
3. 随时更新 `方案.md` 的任务勾选进度，并把进度归档到 `AI-Dev-Harness\state\<项目名>\`；
4. 每一步 git 提交（项目无 git 时先 `git init`）。

### 5.2 4-a 结束与清理
1. 全部任务完成并验证通过后，询问用户「项目已完成，是否满意？是否同意结束？」；
2. 用户同意后，执行清理（见第 6 章「纯净化生命周期」）：
   - 归档 `.harness\` 工作文件到 `AI-Dev-Harness\state\<项目名>\`；
   - 删除项目内的脚手架（`AGENTS.md`、`CLAUDE.md`、`.trae\`、`.harness\`、`.claude\`）；
   - 保留 `.git`、`.gitignore`、`方案.md`、`需求与理念.md` 及全部项目文件；
   - git 提交「纯净版」。

### 5.3 4-b 同步 GitHub（只告知，不代推 —— 锁定决策 5）
1. 清理完成后，询问「是否要同步到 GitHub？」；
2. 用户同意后，**AI 不代用户推送**：只输出一份可直接复制执行的「同步步骤 + 命令」，由用户自己执行；
   - 内容必须齐全：仓库地址/仓库名（用户提供的原文，不擅自编造）、公开或私有、逐条命令、每条命令的预期结果、常见失败的下一步；
   - 步骤输出后**到此为止**，不要顺手把命令跑了 —— "用户点一下就能跑通"才是交付标准；
3. **唯一例外**：用户明确说「你帮我推 / 你代做」时才由 AI 执行 `git remote add` / `git push`，
   并把原始输出（含远端确认）给用户看；执行前仍要先确认仓库地址与公开/私有；
4. 用户自己执行时若报错，AI 只做三件事：读报错原文、说明原因、给下一条命令（不擅自改远端状态）。

### 5.4 4-c 异常处理
- 遇到问题、陷入循环或卡住（如连续 2 轮无进展、超时、方案在当前环境不可行）→ 立即停止，说明原因、影响，给出可行方案；
- 用户选择后继续；不断「执行 → 停止 → 修改 → 再执行」直到完成；
- 实在办不到的，明确说明并移交用户手动执行，并写清怎么做。

### 5.5 4-d 验收与终止
1. 完成所有任务后询问「所有任务是否都完成？请验收」；
2. **验收用脚本跑，不用自述**：跑 `.claude\hooks\verify-gate.mjs`（或项目的验证脚本），原始输出落盘到**工作区根**的 `日志\03-验证\`（第 2 段起日志不再进项目目录），把摘要给用户；
3. 用户验收确认完成并同意停止后，AI 执行全部停止操作：
   - 关闭本次项目过程中开启的所有进程（开发服务器、监控、临时任务等）；
   - 写最终状态报告到 `AI-Dev-Harness\state\<项目名>\`；
   - 输出交付说明（项目在哪、怎么运行、文档在哪）。

## 6. 纯净化生命周期
- 开工 → 生成脚手架（按软件最少化）→ 开发 → 完成 → 用户确认清理 → 归档到 `state\` → 删除脚手架 → 提交纯净版。
- 下次修改同一项目：从 `AI-Dev-Harness\state\<项目名>\` 恢复 → 自动重新生成脚手架 → 改完再清。

## 7. Skills 机制
- 即插即用：`AI-Dev-Harness\自定义\skills\` 下每个含 `SKILL.md` 的文件夹就是一个技能，直接复制进去即可用，**无需登记**。
- **扫描只读摘要（省 token 的关键）**：开工时只读各 `SKILL.md` 的 `name` + `description`，
  或直接跑 `node AI-Dev-Harness\自定义\scripts\list-skills.mjs` 拿索引（约 2 KB / 23 个技能）。
- **要用某个技能时通读它**：`node AI-Dev-Harness\自定义\scripts\list-skills.mjs --show <技能名>` 直接输出该技能全文
  （`--path` 只给路径，便于对大技能用 Read 的 offset/limit 分段读）。一次只读**那一个**；
  超大技能（如 `hatch-pet` 86 KB）按需读它的 `references\`。
- **加/改技能后**跑一次 `node AI-Dev-Harness\自定义\scripts\list-skills.mjs --update` 刷新索引
  （`--check` 可验证是否漂移；不刷新也不影响检索 —— 检索是实时扫描目录，索引只是给人和自检看的快照）。
  **禁止把 `skills\` 下的 `SKILL.md` 全量读入** —— 正文合计约 246 KB（6~8 万 token 级），而一次项目最多用 3~5 个技能。
- 冲突检测（skill-audit）：发现新增/变动技能时，读取所有 `SKILL.md` 检测四类冲突（同名、职责重叠、规则冲突、调用顺序冲突）；发现冲突则用中文向用户说明，并给出选项：
  1. 删除新技能；
  2. 优化新技能使其兼容（AI 改写新技能的 SKILL.md）；
  3. 保留两者（说明各自边界）。
  用户决定后才继续，并把决定记入 `自定义\skills\冲突记录.md`。

## 8. 可改区、内置区与机制层

- **可改区** `自定义\` 里"人能改"的那部分：`流程\`、`skills\`、`templates\`、`项目规则模板\` —— 你随便改。
- **机制层（框架资产）**：工作区根的 `.claude\`、`日志\`，以及 `自定义\` 里的
  `对话协议.md`、`规则源.md`、`模型能力表.json`、`引擎能力表.json`、`scripts\`、`bin\`、`引擎适配\`、`prompt-模板\`
  —— 项目开发期间**不得改动**（`日志\` 只追加，不改写、不提交）。
- **内置区** `内置\`：`adapters\`、`engine\`、`scripts\`、`设计文档\`，默认不要改动。
  **确有必要时**（例如 .ps1 缺 UTF-8 BOM 导致整体解析失败），先在 `state\` 写明「改哪个文件、为什么、怎么回退」，
  **先确认"这是修 harness，不是做项目"**，征得用户同意后再改，改完逐字节核验「只动了该动的地方」。

### 8.1 铁律（框架边界）

**一、项目开发期间只动两处**
只能改动：① 项目文件夹（`我的项目\`，阶段 3 起用项目名）；② `AI-Dev-Harness\state\`（归档与运行态）。
其余任何位置一律不动；需要动，先停下来问用户。

**二、机制层属框架资产，不得修改**
`.claude\`、`自定义\bin\`、`自定义\scripts\`、`自定义\规则源.md`、`自定义\模型能力表.json`、
`自定义\引擎能力表.json`、`自定义\引擎适配\`、`自定义\prompt-模板\`、`日志\`
—— 这些是 harness 的机制层（框架资产），项目开发期间**一律不得改动**
（`日志\` 只追加、不改写：**日志内容不提交**，但说明文件与目录结构随仓库走 —— 否则克隆下来没有日志中心）。

**三、内置区仍不可动（附例外口径）**
`AI-Dev-Harness\内置\`（`adapters\`、`engine\`、`scripts\`、`设计文档\`）仍是不可动区。
**要改内置区或机制层，先确认：「这是修 harness，不是做项目」** —— 用户明确确认后才动，
并在 `state\` 留一条改动记录（改了哪个文件、为什么、怎么回退）。

**四、交付前必须跑纯净度自检**
跑 `node AI-Dev-Harness\自定义\scripts\purity-check.mjs --project "<项目目录>"`，必须返回 0（结论「通过」）：
项目文件夹里不得残留 `.claude\`、`.harness\`、`.trae\`、`AGENTS.md`、`CLAUDE.md`，也不得有 harness 路径引用。
清理先出「将删除 / 将保留」清单、等用户确认（`cleanup.ps1` 不带 `-Confirm` 时一个文件都不删）。

**五、GitHub 只告知，不代推**
远端同步（建仓库、`git remote add`、`git push`、改可见性）默认**只输出步骤与命令**，由用户自己执行；
只有用户明确说「你帮我推 / 你代做」时才代做，且执行后要把原始输出给用户看。

**六、四条老条款继续有效**
1. 所有路径用**相对路径**，不写死绝对路径（工作区可整体复制到任何电脑、任何目录、任何用户名）。
2. **不使用后台常驻进程**、定时任务、开机自启、文件监听；脚本按需运行，收尾关闭本次开启的所有进程。
3. **全程中文**对话。
4. **用户只说话、不输命令**：一切终端与脚本操作由 AI 自行完成。

> **本铁律更新完即锁定**，之后不再改动；要改，先确认"这是修 harness，不是做项目"。

## 10. 硬规则（逐条必须遵守，违反即返工）

> 本章由 `自定义\规则源.md` 自动生成（`gen-rules.mjs --check` 可验证同源），**不要手改**。
> 第 11–13 章是本章的展开（上下文预算 / 验证分层 / 省 token），本章是规则的唯一正文。

**一、改码方式**
改代码只用 Edit / Write 工具。禁止 `sed -i`、`perl -i`、`cat > 源文件`、`python`/`perl` 内联改码
—— 内联替换在 Windows 下会**静默失配**（退出码 0 但文件没改），改坏了你还不知道。
不执行破坏性命令（`rm -rf`、`git reset --hard`、`git push --force`），除非用户明确要求。
不读取、不打印任何密钥 / API key / `.env` 内容。

**二、测试分层（禁止「改一行 → 跑全量」）**
L1 改动后 → 只跑**定向单测**（对应测试文件，秒级）。
L2 任务边界 → 全量单测 + 类型检查（+ lint）。
L3 阶段收尾 → 才跑全量 E2E；配额 2 次 / 会话，**失败不计数**。
每完成一个小功能做最小验证，通过再进下一步。
失败先看 stderr / 日志再改，禁止「猜 → 改 → 重跑」。
验收不达标 → 如实记录，禁止造假数据、禁止把失败说成通过。

**三、上下文与成本（省 token 六策略）**
1. **分层加载**：只读当前任务相关文件，不通读整库。
2. **忽略大目录**：`node_modules`、`dist`、`.git`、构建产物一律不读、不 grep。
3. **记忆外置**：已读摘要与关键决策写进 `.harness\`（JOURNAL / HANDOFF），靠文件记，不靠上下文记。

## 11. 上下文预算与会话切分

### 11.1 上下文预算
- **单会话上下文用量不超过 70%**。到 70% 就结束会话、写 HANDOFF、让用户开新会话。
- 不要硬撑到自动压缩：压缩会丢细节，且压缩后的每一轮都要重读整份摘要（这正是上次事故的形态）。
- 当前水位可以看状态栏（`上下文 X% │ 5h Y% │ 缓存 Z`）；`Stop` hook 会在超 70% 时拒绝结束并提示。

### 11.2 4 条硬性终止条件（满足任何一条就必须收尾，不商量）
1. 上下文用量 ≥ 70%；
2. 连续 2 轮无实质进展；
3. 单个文件被反复修改 ≥ 8 次仍未通过验证；
4. 任务阶段完成（一个小阶段收尾后主动收尾，不要顺势开启新阶段）。

终止时必须：写 `.harness\HANDOFF.md`（当前任务 / 已完成 / 下一步 / 关键决策与坑 / 环境），然后结束会话。

## 12. 验证分层与禁止矩阵

### 12.1 三层
| 层 | 时机 | 跑什么 | 配额 |
|---|---|---|---|
| **L1 定向** | 每次改完一处 | 对应测试文件（如 `npx vitest run src/a.spec.ts`），秒级 | 不限 |
| **L2 边界** | 一个小功能做完 | 全量单测 + 类型检查（+ lint） | 不限 |
| **L3 收尾** | 阶段收尾（4-a / 4-d） | 全量 E2E | **2 次/会话，失败不计数** |

`内置\scripts\verify.ps1` 跑的是完整 `npm test`，属于 **L2**（不是 L1）。
「每完成一个小功能做最小验证」里的「最小验证」= **L1**。

### 12.2 禁止矩阵
| 禁止 | 为什么 |
|---|---|
| 改一行 → 跑全量 E2E | 上次 131 次 / 102 分钟，占 Bash 耗时 45% |
| 跳过 L1 直接 L2 / L3 | 定位成本成倍上升 |
| 用 shell / python 内联改码 | Windows 下静默失配 |
| 把整屏日志灌进上下文 | 数万 token 白烧 |
| 未读日志就重跑失败命令 | 同因同果 |
| 把未验证内容当作已完成 | 用户无法信任完成度 |
| 为了省钱而跳过该跑的 L1 | 省 token 不能拿质量换 |

### 12.3 独立验收（G11）
需要「可被引用的证据」时，跑 `.claude\hooks\verify-gate.mjs`：**脚本跑命令、原始输出落盘**，
模型只能引用脚本输出，**不许自己总结成「已全部通过」**。

## 14. 机制层（知道它存在，也要知道它的边界）

工作区根有 `.claude\`（hooks）。它由 harness 维护，AI **不需要改它**，但必须知道：

| 机制 | 做什么 | 覆盖边界（如实说明） |
|---|---|---|
| `guard-bash.mjs` | 拦 `sed -i` / `cat >` / python 内联改码 / 长 `sleep`；E2E 配额记账；G10 把测试/构建类命令的输出窄化 | 只拦 shell 命令；E2E 成功才计数，失败不计数；本机没有真 bash 时 G10 **放弃改写**（不产出跑不通的命令） |
| `guard-tools.mjs` | 大文件第 2 次全读、同文件第 8 次修改 → **只警告不拦** | 只警告 |
| `inject-rules.mjs` | 每次会话开始把硬规则 + 上次 HANDOFF 注入上下文 | 只在 Claude Code 生效 |
| `shape-output.mjs` | 长输出落盘 + 给一行路径提示 | **不替换模型看到的原文**（本版本无此机制），所以长输出命令仍应自己重定向 |
| `on-stop.mjs` | 生成 HANDOFF；上下文超 70% 拒绝结束（有防死循环）；会话正常收尾时上报自主学习 | 只在 Claude Code 生效 |
| `statusline.mjs` | 状态栏显示上下文水位；窗口变化时上报自主学习 | 只在 Claude Code 生效 |
| `verify-gate.mjs` | 独立验收，原始输出落盘 | 手动调用 |
| 命令包装（G10） | 对测试 / 构建 / 类型检查类命令做**窄范围**改写，把长输出导向摘要器 | 只覆盖窄名单；`vitest --watch` 这类长驻命令不包装；模型会看到被改写的命令串 |
| `自定义\scripts\purity-check.mjs` | 交付前纯净度自检：项目里不得有 `.claude\` / `.harness\` / `.trae\` / `AGENTS.md` / `CLAUDE.md` 与 harness 路径引用 | 有界扫描（文本类扩展名、≤256 KB/文件、≤3000 文件）；二进制不扫 |
