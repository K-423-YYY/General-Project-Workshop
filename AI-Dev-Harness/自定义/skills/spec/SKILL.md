# Spec（SDD 规范驱动开发）

> 本技能由两个角色文档组成，**同一件事的两个阶段**：
> - `spec-writer.md` —— 生成 / 修改规范（**只写规范，不写代码**）
> - `spec-checker.md` —— 拿验收标准逐项核对实现（输出 `SPEC_PASS` / `SPEC_FAIL`）
>
> 第 3 段（P3-1）补上这个 `SKILL.md`：`skills-usage.md` 约定「每个技能文件夹必须有 SKILL.md」，
> 而 `spec\` 之前只有两个角色文档，**按约定扫不到、也就等于不会被调用**。这里补齐约定所需的最小外壳。

## 适用场景

- 用户提了一个**新功能**，但还没说清要做什么、不做什么 → 先用 `spec-writer` 出规范。
- 开发做完一轮，要判断「是不是真的做完了」 → 用 `spec-checker` 逐项核对。
- 计划书 / 需求与理念 已存在，但缺**可判定的验收标准** → 回到 `spec-writer` 补第 5 节。

## 必须遵守规则

1. **先规范、后代码**：`spec-writer` 阶段不许写实现代码，也不许顺手改项目文件。
2. **验收标准必须可判定**：写成「能跑哪条命令、看什么输出、什么算通过」，不写「体验流畅」这种没法判的话。
3. **单任务单轮可完成**：超出的必须拆成子任务并给出各自验收标准。
4. **范围外要写明**：明确列出本期**不做**的事（这一条能省掉最多的返工）。
5. **没批准不动手**：规范写完等用户回 `APPROVED` 才交给执行阶段。
6. **核对要说实话**：`spec-checker` 判不了的一律写「无法验证」并说明原因，不许猜成「通过」。

## 执行步骤

1. 读输入：用户需求 / `项目说明\01-项目需求与理念.md` / `自定义\templates\需求与理念模板.md`。
2. 按 `spec-writer.md` 的六节结构产出规范（核心目标 / 需求补全 / 文件变更范围 / 任务分解 / 验收标准 / 验证方式）。
3. 任务分解表逐项标注优先级（P0/P1）与「是否单轮可完成」；过大的当场拆开。
4. 输出规范，**等用户 `APPROVED`**。
5. 开发完成后跑 `spec-checker.md` 的流程：逐项判 通过 / 未通过 / 无法验证，报告追加到 `docs/CHECKPOINTS.md`（没有该文件就写到项目 `.harness\`）。
6. 有未通过项 → 末行 `SPEC_FAIL` + 原因；全通过 → `SPEC_PASS`。

## 验证方式

- 规范六节齐全，且第 5 节每条验收标准都能对应一条可执行的验证命令。
- 任务分解表里没有「单轮做不完」的条目（有就必须已拆分）。
- `spec-checker` 的每一项判定都有证据（命令输出 / 文件位置），没有凭空的「通过」。

## 禁止行为

- 禁止在规范阶段写实现代码、改项目业务文件。
- 禁止把「无法验证」写成「通过」。
- 禁止自行扩大范围（范围外的事写进第 2 节的「范围外内容」，而不是顺手做掉）。
- 禁止跳过用户批准直接进入执行。

## 成功判定

- 用户对规范回 `APPROVED`。
- 开发完成后 `spec-checker` 输出 `SPEC_PASS`（全部通过），或输出 `SPEC_FAIL` 且每条未通过项都有明确原因与下一步。
