# Backend API Skill

## 1. 设计原则

- API 围绕资源设计，使用名词复数路径（`/users`、`/orders`）。
- 用 HTTP 方法表达动作：GET 查询、POST 创建、PUT/PATCH 更新、DELETE 删除。
- 路径使用 kebab-case，字段使用 camelCase，版本放在路径前缀（`/api/v1`）。
- 路由层只做参数解析、调用服务、返回响应，不内嵌业务规则。

## 2. 路由与资源

- 子资源仅在有明确从属关系时使用（`/users/:id/orders`）。
- 复杂查询使用显式参数：page、pageSize、sort、filter，不发明自定义查询语法。
- POST 创建返回 201 和 Location；PUT 更新返回 200；DELETE 返回 204。

## 3. 状态码

- 200 成功；201 创建成功；204 无内容。
- 400 参数错误；401 未认证；403 无权限；404 资源不存在；409 冲突；422 业务校验失败；429 限流；500 内部错误。
- 不要把业务失败伪装成 500，也不要用 4xx 掩盖内部错误。

## 4. 请求校验

- query、params、body、headers 都必须校验。
- 使用 Zod、Joi、Pydantic 等声明式校验库，不手写散落的 if 校验。
- 校验失败返回统一的 400/422 错误结构。

## 5. 错误响应

- 统一错误结构：`{ "error": { "code", "message", "details" } }`。
- code 是稳定机器可读错误码，message 是用户可读信息，details 是字段级信息。
- 日志记录内部堆栈，但响应不暴露堆栈、SQL、密钥。

## 6. 鉴权与授权

- 认证优先使用成熟方案：JWT、OAuth2、Session + Cookie。
- 中间件统一校验身份，资源级权限在业务层校验。
- 密码使用 bcrypt/argon2 哈希；密钥放环境变量，不提交仓库。

## 7. 数据与性能

- 查询加索引；列表接口必须分页并限制最大 pageSize。
- 返回字段避免 N+1 查询；敏感字段在序列化层剔除。
- 耗时任务使用后台队列，接口只返回任务状态。

## 8. 接口文档

- 使用 OpenAPI/Swagger 生成文档，保持文档与实现同源。
- 每个接口写明参数、示例和错误码。

## 9. 测试

- 服务层单测覆盖业务规则；接口层使用 supertest/httpx 等做集成测试。
- 测试隔离：使用内存数据库或测试数据库，不依赖真实外部服务。
- 鉴权失败、校验失败、404、重复创建等边界必须有测试。

## 10. 验收检查清单

- [ ] 路由符合 RESTful 命名
- [ ] 所有输入有声明式校验
- [ ] 错误响应结构统一且不泄露内部信息
- [ ] 鉴权中间件已生效并覆盖资源权限
- [ ] 列表接口分页、排序参数明确
- [ ] OpenAPI 文档与实现同步
- [ ] 核心业务路径有集成测试
