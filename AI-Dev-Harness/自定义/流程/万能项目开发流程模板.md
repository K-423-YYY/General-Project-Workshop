# 万能项目开发流程（完整标准模板）

## 一、总则

### 1.1 适用范围
适用于所有由 AI 辅助完成的项目开发任务，包括但不限于：网站、应用、工具、脚本、自动化流程、文档型项目、开源项目发布。

### 1.2 执行优先级
1. 遇到模板中已列出的同类问题，第一方案必须是模板中的方案，先执行模板方案。
2. 模板方案失败后，先向用户提示，再尝试其他方法。
3. 不得在没有先执行模板方案的情况下自由发挥。

### 1.3 过程约束
1. 整个项目必须严格按照“项目计划书 + 项目需求 + 项目理念”执行。
2. AI 不得擅自修改：项目目标、项目范围、交付物、验收标准、技术方向、计划任务顺序。
3. 计划中没有的内容，默认不添加；计划中已有的内容，默认不删除。
4. AI 只能提出建议，不能代替用户做方向性决策。

### 1.4 异常处理
当出现以下情况时，必须先停止该部分执行，向用户说明问题、影响和可选方案，由用户决定后再继续：
1. 计划书、需求或理念文档之间存在冲突；
2. 计划内容缺失、模糊、无法理解；
3. 计划中的目标或方案在当前环境下不可行；
4. 执行过程中发现计划需要调整；
5. 模板方案全部失败，没有其他可确认的下一步。

### 1.5 验证原则
1. 每完成一个步骤，做一次最小验证。
2. 验证通过才能进入下一步。
3. 验证失败时，先按模板方案处理。
4. 模板方案处理后仍失败，向用户提示并询问。

### 1.6 停止原则
只有在以下三种情况下才停止：
1. 需要用户手动操作或用户决策；
2. 当前任务完全不可行；
3. 所有任务已经完成并确认。

### 1.7 手动移交原则
当整个项目进行过程中，任何 AI 办不到、或者重复几轮之后还是办不到的地方，直接交给用户手动执行，并明确说明怎么执行。

## 二、角色与责任

### 用户负责
1. 提供项目目标、计划书、需求文档、理念文档。
2. 确认项目范围和验收标准。
3. 在异常时决定方向。
4. 在自动化环境无法完成时执行必要的手动操作。

### AI 负责
1. 只读检查项目现状和文档。
2. 按计划执行全部可自动化步骤。
3. 完成本地验证和交付。
4. 发现异常时及时、明确地向用户报告。
5. 收尾清理并输出使用说明。

## 三、完整执行流程

### 步骤 0：前置确认
目标：确认任务可以开始。
动作：
1. 确认项目计划书、需求文档、理念文档存在。
2. 确认交付物和验收标准。
3. 确认环境：git、npm、node、codex、网络、GitHub 登录状态。
4. 确认自动化长任务脚本是否已安装。
产出：任务清单、环境清单。

### 步骤 1：读取与检查
目标：了解项目，不改动任何文件。
动作：
1. 读取全部需求、计划、理念文档。
2. 列出项目目录结构和当前完成状态。
3. 检查 git 状态、现有代码、现有脚本。
4. 标记文档中的模糊点、冲突点、不可行点。
5. 如果发现异常，按“异常处理”规则向用户提示。
产出：项目现状报告、待确认问题清单。

### 步骤 2：安装并配置自动化长任务脚本
目标：让后续长任务可以循环执行、中断恢复。
动作：
1. 全局安装：
   ```powershell
   npm install -g codex-autoresearch
   ```
2. 确认版本：
   ```powershell
   codex-autoresearch --version
   ```
3. 配置可执行文件：
   - 找到原生 `codex.exe` 的真实路径；
   - 设置用户环境变量：
     ```powershell
     [Environment]::SetEnvironmentVariable("CODEX_BIN", "原生codex.exe完整路径", "User")
     ```
4. 适配当前 Codex CLI：
   - 查看当前参数：`codex exec --help`
   - 如果当前 CLI 不支持 `--full-auto`：
     ```powershell
     [Environment]::SetEnvironmentVariable("USE_FULL_AUTO", "0", "User")
     ```
5. 配置可写沙箱：
   - 在 `~/.codex/config.toml` 添加：
     ```toml
     sandbox_mode = "workspace-write"
     ```
   - 修改前先备份原配置。
6. 小任务验证：
   ```powershell
   codex-autoresearch --no-full-auto --skip-git-repo-check --no-stream run "只回复 OK"
   ```
   确认输出 `status: completed`。
产出：可用的自动化长任务脚本。

### 步骤 3：按计划梳理任务
目标：把项目目标拆成可执行任务。
动作：
1. 从计划书中提取任务清单。
2. 每个任务写明：
   - 编号；
   - 目标；
   - 优先级；
   - 验收标准；
   - 是否单轮可完成；
   - 依赖关系。
3. 将任务清单与计划书逐项比对。
4. 发现缺失、冲突、不可行时，提示用户。
产出：任务拆分表。

### 步骤 4：搭建项目骨架
目标：创建计划要求的项目结构。
动作：
1. 只创建计划书要求的目录和文件。
2. 包括：入口脚本、验证脚本、技能规范、说明文档、示例文件、配置文件。
3. 不添加计划外内容。
4. 完成后列出新增文件清单。
产出：项目骨架。

### 步骤 5：本地验证
目标：确保项目骨架可用。
动作：
1. 语法检查：
   ```powershell
   bash -n 脚本.sh
   ```
   PowerShell 脚本用语法解析检查。
2. 编码检查：
   - `.ps1` 统一 UTF-8 BOM；
   - 中文内容不得乱码。
3. 冒烟测试：
   - 用假执行器跑通主要流程；
   - 验证生成、执行、完成、修改等路径。
4. 真实连通测试：
   - 用真实 CLI 做一次最小调用；
   - 确认模型、API、网络可用。
5. 自动化脚本自测：
   - 运行 `selftest` 类脚本，确认脚本本身可重复运行。
产出：验证通过记录。

### 步骤 6：执行主任务
目标：按计划完成全部开发任务。
动作：
1. 创建任务提示文件 `prompt.md`，包含：
   - 不可变目标；
   - 可变执行步骤；
   - 验收标准。
2. 使用自动化脚本执行：
   ```powershell
   codex-autoresearch --no-full-auto --skip-git-repo-check --no-stream run --prompt-file .\prompt.md --frozen-goals-text "..."
   ```
3. 中断后恢复：
   ```powershell
   codex-autoresearch session resume --last
   ```
4. 执行过程中严格按计划书：
   - 不擅自扩大范围；
   - 不擅自改变实现方式；
   - 发现需要偏离计划时，先停下询问用户。
产出：已完成的项目代码和文档。

### 步骤 7：异常处理流程
触发条件：
1. 模板方案失败；
2. 计划不可行；
3. 网络/凭据/权限不足；
4. 计划与需求冲突。

处理动作：
1. 停止当前部分执行。
2. 向用户报告：
   - 当前进度；
   - 具体问题；
   - 已尝试的方案；
   - 可选方案；
   - 需要用户做什么。
3. 等待用户决定。
4. 用户决定后，按决定继续执行。
产出：异常处理记录、用户决定。

### 步骤 8：集成与交付
目标：把项目变成可交付的仓库。
动作：
1. 初始化 git：
   ```powershell
   git init -b main
   ```
2. 创建 `.gitignore`：
   - 排除运行状态目录；
   - 排除临时目录；
   - 排除依赖目录；
   - 排除构建产物；
   - 排除敏感文件。
3. 检查未跟踪文件：
   ```powershell
   git status
   ```
4. 只提交计划内文件：
   ```powershell
   git add -A
   git commit -m "项目提交说明"
   ```
5. 创建远程仓库：
   - 用 GitHub API 或浏览器创建公开/私有仓库。
6. 配置远程：
   ```powershell
   git remote add origin https://github.com/用户名/仓库名.git
   ```
7. 推送：
   ```powershell
   git push -u origin main
   ```
产出：本地仓库、远程仓库、提交记录。

### 步骤 9：远程验证
目标：确认远程内容正确。
动作：
1. 检查远程分支：
   ```powershell
   git ls-remote origin
   ```
2. 确认本地与远程提交一致：
   ```powershell
   git log --oneline -1
   git rev-parse HEAD
   ```
3. 确认远程仓库文件清单正确。
4. 如无法从自动化环境访问远程，请用户浏览器确认。
产出：远程验证结果。

### 步骤 10：清理临时文件
目标：项目目录保持干净。
动作：
1. 删除运行状态目录：`.codex-run/`。
2. 删除临时测试目录。
3. 删除日志文件。
4. 删除任务提示文件 `prompt.md`（如不再需要）。
5. 检查根目录：
   ```powershell
   Get-ChildItem -Force
   git status
   ```
6. 确保没有多余文件。
产出：纯净项目目录。

### 步骤 11：输出最终说明
内容：
1. 项目地址；
2. 提交 SHA；
3. 项目结构说明；
4. 使用方式；
5. 自动化脚本用法；
6. 后续维护命令。
产出：最终交付说明。

### 步骤 12：用户确认
1. 用户确认远程内容正确。
2. 用户确认交付物和验收标准已满足。
3. 全部确认后，任务正式完成。

## 四、通用问题与解决方案

| 问题 | 第一方案 | 备用方案 | 是否需要手动 |
|---|---|---|---|
| 网络代理失败 | 清掉 `http_proxy/https_proxy/all_proxy` 后直连重试 | 换可用代理/镜像 | 否 |
| CLI 版本参数变化 | 先看 `--version` 和 `--help`，按当前版本参数执行 | 提示用户确认 | 否 |
| 脚本 `spawn EPERM` | 设置 `CODEX_BIN` 指向原生可执行文件 | 重建全局链接 | 否 |
| 脚本子进程只读沙箱 | 配置 `sandbox_mode = "workspace-write"` | 在普通终端运行脚本 | 否 |
| 子进程无网络/凭据 | 停止脚本，提示用户 | 用户手动执行 | 是 |
| 长任务被中断 | `codex-autoresearch session resume --last` | 重新创建任务 | 否 |
| 执行策略阻止脚本 | 使用 `npm.cmd` 等兼容入口 | 修改执行策略前询问用户 | 否 |
| 中文乱码 | 统一 UTF-8 BOM | 转换编码 | 否 |
| 空仓库 API 上传失败 | 先创建初始文件再上传 | 手动推送 | 否 |
| 推送网络不稳定 | 重试推送 | 用户手动推送 | 是 |
| 仓库名冲突 | 换一个仓库名并提示用户 | 复用已有仓库 | 是 |
| 凭据不可用 | 提示用户检查登录状态 | 用户重新登录/生成 token | 是 |
| 计划/需求有问题 | 停止执行，向用户说明 | 等待用户决定 | 是 |

## 五、需要用户手动或决策的情况

1. 计划书、需求、理念有问题或不可行时，由用户决定方向。
2. 自动化环境无法访问网络、凭据、系统权限时，用户手动执行最简命令。
3. 模板第一方案失败且没有可靠替代方案时，先询问用户。
4. 涉及账号、权限、敏感信息、公开发布等操作时，用户确认后再执行。

## 六、禁止行为

1. 禁止擅自修改项目目标、范围、验收标准。
2. 禁止绕过计划书自行发挥。
3. 禁止隐瞒异常、失败、偏差。
4. 禁止把临时方案当成最终方案。
5. 禁止在用户未决定前继续执行有争议部分。
6. 禁止擅自删除计划内文件。
7. 禁止未经确认执行敏感操作。

## 七、成功判定标准

1. 所有任务均按计划书完成并通过验证。
2. 本地无未提交改动。
3. 远程仓库可访问且内容正确。
4. 无临时文件残留。
5. 交付结果经用户确认。
