# 01 · 项目需求与理念

> 本文档汇总整套「AI 通用项目开发工作区」的全部需求、设计理念与核心逻辑。
> 一句话定位：**把本文件夹复制给任意 AI，用中文对话完成一个完整、纯净的项目。**

---

## 一、这个项目是什么

一个**可整体复制、可交付给任意 AI 的通用项目开发配置包**。它不写死任何具体业务，只提供一套规则和流程：让 Codex、Claude Code、DeepSeek Harness、Trae 等 AI，在对话框里用中文一步步完成「需求 → 方案 → 文档 → 命名 → 开发 → 验证 → 清理 → GitHub」的全过程，最终留下一个纯净、完整的项目。

---

## 二、完整需求清单（逐条收录）

### 2.1 通用性
1. 小作业必须是通用的，不局限于某一种项目类型。
2. Codex 使用对话框（客户端对话界面）。
3. Claude Code：客户端用客户端对话框，终端用终端对话框。
4. DeepSeek Harness：无论终端还是客户端，全部使用汉语对话。
5. 适配 4 个软件、8 种形态：Codex 客户端；Claude Code 客户端 + 终端；DeepSeek Harness（客户端 + 终端）；Trae IDE 国内版 + 国际版；TraeWork 桌面版；TraeCode CLI。

### 2.2 交互方式
1. 所有交互一律使用**中文对话**，不用命令。
2. 不限定必须使用哪一套汉语对话，可灵活使用任意 AI。

### 2.3 执行流程
1. (a) 读取用户意图并反馈。
2. (b) 通过一步步对话，完成项目需要的内容与结构。
3. (c) 经过判断、用户确认后再开始执行。
4. (d) 执行中遇到问题，中断并询问，给出方案后继续执行。
5. 细化为五个阶段（见第四章）：开工 → 方案沟通确认 → 双文档生成 → 项目命名 → 执行交付。

### 2.4 核心目标
- 强化交互性，灵活使用汉语语言，而不是指令。

### 2.5 位置与结构
1. Harness 放在 本文件夹 根目录，与「我的项目」文件夹同级。
2. Harness 不放进项目文件夹内部。
3. Harness 内部拆成「可改区」与「内置区」，隔离区分。

### 2.6 使用方式
1. 用户把整个文件夹复制出来交给 AI。
2. AI 询问要做什么项目并起名字。
3. AI 把「我的项目」文件夹改名为项目名。
4. AI 用 Harness 的配置完成该项目。

### 2.7 Skills 机制
1. 即插即用：把含 `SKILL.md` 的文件夹复制进 `skills\` 即可用，无需登记。
2. 冲突检测：新增技能时判断与原有技能是否冲突。
3. 冲突处理：通过对话向用户提出建议，让用户决定删除 / 优化 / 保留两者。

### 2.8 纯净化
1. 项目文件夹尽量少含与项目无关的配置。
2. 开发期允许存在脚手架配置，项目完成后自动清除。
3. 下次修改时脚手架自动重新生成，改完再自动删除，始终保持纯净交付。

### 2.9 其他已确认项
1. 清理前 AI 先问一句「确认清理并提交纯净版」，用户同意才动手。
2. `.git` 与 `.gitignore` 保留（属于项目工程配置）。
3. 复制 `~/.codex/skills` 里的其他技能（含官方开发技能）到 `skills\`。
4. 可复制：所有路径使用相对路径，复制到任何电脑、任何用户名都能用。
5. 无后台：不使用时不在后台运行任何进程（无定时任务、开机自启、文件监听）。

## 三、设计理念

| 理念 | 说明 |
|---|---|
| 对话优先 | 用户只说话，不输命令；AI 在后台自行完成脚本/终端操作 |
| 通用复用 | 一套配置适配 8 种软件形态；一个文件夹复制即用 |
| 纯净交付 | 用完即净：脚手架开发期存在、完成后归档并删除 |
| 隔离清晰 | 「可改区」你随便改，「内置区」不用你改，互不干扰 |
| 可控可停 | 每个关键节点（方案、命名、开始、清理、GitHub、停止）都先问你 |
| 省心省资源 | 无后台进程；脚本按需运行，收尾关闭所有进程 |

---

## 四、核心逻辑

### 4.1 对话协作协议（a–e）
- (a) 收到需求先复述确认，指出不清楚处，不急着动手。
- (b) 一步步中文对话，把目标/功能/结构/技术/验收聊清楚，写进项目文档。
- (c) 方案经用户确认后才开始执行，每完成一小步做最小验证。
- (d) 遇到问题、要用户决策、涉及敏感操作时，停下询问并给方案。
- (e) 收尾纯净化：完成后先问「确认清理并提交纯净版」，再归档、删除脚手架、提交。

### 4.2 五个阶段
1. **阶段 0 开工**：AI 中文问候，询问「想做什么项目？」并复述确认。
2. **阶段 1 方案沟通确认**：对话细化需求，AI 输出「方案清单草稿」（需求+理念+模块+结构+验收），反复改到用户确认。
3. **阶段 2 双文档生成**：生成 `方案.md` 与 `需求与理念.md`，存进项目文件夹，永久保留。
4. **阶段 3 项目命名**：AI 推荐 3–5 个名字或用户自定；确定后重命名「我的项目」为项目名，并写回两份文档。
5. **阶段 4 执行交付**：
   - 4-a 结束清理：完成后先问「满意吗？同意结束吗？」，同意才清理。
   - 4-b 同步 GitHub：清理完成后才问是否同步，索要仓库信息后执行。
   - 4-c 异常处理：卡住/循环/不可行 → 停止、说明原因、给方案，反复执行-停止-修改直到完成。
   - 4-d 验收终止：问「所有任务完成了吗？」，验收通过并同意后才停止所有进程并交付。

### 4.3 纯净化生命周期
```
开工 → 生成脚手架（按软件最少化）→ 开发 → 完成
   → 用户确认清理 → 归档到 state\ → 删除脚手架 → 提交纯净版
   → 下次修改：从 state\ 恢复 → 自动重新生成 → 改完再清
```

### 4.4 异常 / 停止 / 手动移交原则
- 只有三种情况停止：需要用户手动/决策、任务完全不可行、全部完成并确认。
- 办不到或反复办不到的地方，明确移交用户手动执行，并写清怎么做。
- 不擅自修改目标、范围、交付物、验收标准；AI 只提建议。
